## 1. 新地址：这是一个"诱饵端点"

### 1.1 播放清单请求矩阵

| 请求变体 | HTTP | 字节 | 内容 md5 |
|---|---|---|---|
| 原始路径 `…/640x360/video.m3u8` | 200 | 122 | `114DCAE3…A165CD` |
| 同级 `…/playlist.m3u8` / `master.m3u8` / `video.m3u8` | 200 | 122 | 同上 |
| 上跳一级 `/{token}/playlist.m3u8` | 200 | 122 | 同上 |
| 换分辨率 `720x1280` / `1080x1920` / `320x180` / `1280x720` | 200 | 122 | 同上 |
| **伪造不存在的文件** `…/640x360/nonexistent.m3u8` | 200 | 122 | 同上 |
| **伪造 token** `/AAAA/0447d70…/640x360/video.m3u8` | 200 | 122 | 同上 |
| **伪造 mediaId** `/{token}/99999999/640x360/video.m3u8` | 200 | 122 | 同上 |
| 站点根路径 `https://m3cdn.playergo.top/anything.m3u8` | 200 | 122 | 同上 |

返回内容恒为：

```
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:8
#EXT-X-MEDIA-SEQUENCE:0
#EXTINF:8.000000,
video20000.jpeg
#EXT-X-ENDLIST
```

**"不存在的文件"和"伪造的 token"返回的内容与真实路径完全一致** —— 这已经不是"路径写错"，而是 CDN 上的一条**兜底诱饵路由**。

### 1.2 分片请求矩阵（同一"诱饵目录"下）

| 分片索引 | HTTP | 字节 | md5 |
|---|---|---|---|
| 0, 1, 2, 3, 7, 15, 63, 127, 255, 511, 1023, 2000 | 200 | 56024 | `2BFBB28E…1F35A80E` |
| 20001, 20002, 20003 | 200 | 56024 | 同上 |
| 20000 | 404 | 430 | OSS `NoSuchKey` |

所有分片逐字节相同（`sha256 = E4FD8085…99B0442`）。唯一的 404 说明请求确实打到了阿里云 OSS 桶 `surrit.oss-eu-central-1`，而该 bucket 匿名不可读、直连返回 `NoSuchBucket` / `AccessDenied`。

### 1.3 排除法

| 假设 | 实验 | 结果 |
|---|---|---|
| 是 UA / Referer / Origin 触发了拦截 | 加浏览器 UA、加 Referer、加 Origin、加全套浏览器头 | 内容不变 |
| 是本机代理导致的 | `curl --noproxy "*"` 直连 | 内容不变 |
| 是 Cloudflare 缓存旧响应 | 追加随机 query、`Cache-Control: no-cache`、`Pragma: no-cache` | 仍为同一份诱饵，`cf-cache-status: HIT` |
| 是路径写错 | 伪造不存在的文件名 / token / mediaId | 仍返回同一条诱饵 ⇒ 不是路径问题 |

**四条假设全部排除。结论：该媒体路径在服务端没有对应内容。**

## 2. 诱饵长什么样：它是一段"合法 TS"

对 56024 字节的诱饵做 `ffprobe`：

| 字段 | 值 |
|---|---|
| format | `mpegts`（MPEG-TS） |
| 时长 | 8.023222 s |
| 码率 | 55861 bit/s（≈ 55 kbps） |
| 视频 | h264 Main，**1280x720**，25 fps，8.000000 s |
| 音频 | aac LC，44100 Hz，stereo，7.825122 s |
| 首字节 | `47`（合法 TS 同步字） |

两个后果：

1. **路径声明 `640x360`，诱饵实际是 `1280x720`** —— 分片内容与所选清晰度不符。
2. **它不是"坏数据"，而是一段格式完全合法的 TS**。任何"检查 0x47 同步字"、"让 ffmpeg 试着解一下"的校验策略，都会把它判定为**合格分片**。

## 3. `crypt.key`：真实流是 AES-128，而且不在同一个域

| 项 | 值 |
|---|---|
| HTTP | 200 OK |
| 长度 | 16 字节（标准 AES-128 密钥长度） |
| 签名参数 | `auth_key=1789227019-90-0-65f0a34f0daba36fe344dce736a6e2de` |
| 服务器 | nginx → CloudFront（`X-Cache: Miss from cloudfront`） |

`auth_key=<时间戳>-<随机数>-<uid>-<md5>` 是**腾讯云 CDN TypeA 签名**格式，签名与 **URL 路径绑定**。用它去猜该域上的其它路径：

| 猜测路径 | 结果 |
|---|---|
| `/videos5/{hash}/playlist.m3u8?auth_key=…` | 403 |
| `/videos5/{hash}/640x360/video.m3u8?auth_key=…` | 403 |
| `/videos5/{hash}/` | 403 |
| `/videos5/{hash}/640x360/video00000.jpeg?auth_key=…` | 403 |
| `/videos5/{hash}/crypt.key?auth_key=…` | **200** |

**推导**：真实内容确实是 **AES-128 加密的 HLS**，位于 `as.oolrvd.cn`；我们只拿到了 `crypt.key` 这一条路径的签名，拿不到 m3u8 的签名。而 playergo 侧的清单里**没有 `#EXT-X-KEY` 标签**。因此这两条 URL 拼不出一个可下载的地址。

## 4. 对照组：上一轮的旧地址仍然可用，但被"占位"污染

### 4.1 清单结构正常

| 层级 | 结果 |
|---|---|
| `/{oldToken}/46059518b63269/playlist.m3u8` | 439 字节，含 `#EXT-X-TOKEN=`，2 档清晰度：`640x360 @800k`、`842x480 @1400k` |
| `.../640x360/video.m3u8` | 42988 字节，**1331 个分片**，总时长 **5323.42 s = 88.72 分钟**，`#EXT-X-PLAYLIST-TYPE:VOD` |

### 4.2 分片实测：**约 27% 是占位假片**

先用 `Range: bytes=0-0` 做 1 字节探测（读 `Content-Range` 拿真实长度），抽样 56 个点：

| 区间 | 结果 |
|---|---|
| video0 ~ video5 | **全部占位**（6 连） |
| video6 ~ video39、60、80、100 | 全部真实（163 KB ~ 612 KB，大小各不相同） |
| video150、200、300、500 | **占位** |
| video400、600、700、800 | 真实 |
| video900、1000、1100、1200、1300 | **全部占位**（尾部 5 连） |
| **合计** | 抽样 56 → 真实 41 / 占位 15 ⇒ **占位率 26.8%** |

两类分片的**可区分特征**：

| 特征 | 占位分片 | 真实分片 |
|---|---|---|
| 字节数 | 恒定 56024 | 随内容变化（163 KB ~ 612 KB） |
| md5 | 恒定 `2BFBB28E…1F35A80E` | 各不相同 |
| ETag | `"6a794ab7-dad8"` | 无 |
| Last-Modified | **2026-08-10 03:51:19** | **2024-01-20**（源文件时间） |
| cf-cache-status | HIT（已固化进边缘缓存） | MISS / 各异 |

> 注意 `Last-Modified` 的后缀 `-dad8` 正好等于 `56024` 的十六进制 —— 这 56024 字节是**被当作一个真实对象缓存下来的**，而不是实时生成的。

### 4.3 污染无法在客户端绕开（实测 10 种手段）

对已污染的 `video0.jpeg` 逐一尝试：

| 手段 | 结果 |
|---|---|
| 原始请求 | 56024 DECOY，`HIT` |
| 追加随机 query `?cb=777001` | 56024 DECOY，`HIT` |
| `Cache-Control: no-cache` | 56024 DECOY，`HIT` |
| `Pragma: no-cache` | 56024 DECOY，`HIT` |
| `Cache-Control: no-cache, no-store, max-age=0` | 56024 DECOY，`HIT` |
| `Range: bytes=0-1023` | 返回范围数据（仍来自同一份 56024 对象） |
| 路径加 `./` | 56024 DECOY，`HIT` |
| 路径加双斜杠 `//` | 56024 DECOY，`HIT` |
| **绕过本机代理直连** | 56024 DECOY，`HIT` |
| **换 iPhone UA** | 56024 DECOY，`HIT` |

**全部失败。** 这说明该 CDN 的缓存键忽略 query string 与路径归一化差异，一旦某个分片被诱饵污染，客户端在快到期前（`max-age=2678400` = 31 天）**无法自救**。

## 5. 为什么表现为"下载不完整 / 花屏 / 音画不同步"

| 环节 | 现象 |
|---|---|
| 时长错位 | 诱饵恒为 **8.000 s**，而清单声明该分片是 **5.000 s / 2.500 s**。拼接后时间轴被拉长，音画必然逐步错位。 |
| 内容重复 | 被污染的分片全片重复同一段 8 秒画面，观感就是"卡住 / 黑屏 / 画面不动"。 |
| 静默成功 | ffmpeg 能正常解码这段合法 TS，因此**退出码为 0**，工具判定"下载成功"，用户拿到一个坏文件却不知道为什么。 |
| 无法重试 | 重试命中同一条缓存诱饵，纯浪费配额。 |
| **代码层面** | 全仓库检索确认：**不存在任何分片内容校验、重复检测、哈希比对的代码**。当前实现会把坏分片当好分片直接用。 |

## 6. 由证据推出的硬性要求

| 编号 | 要求 | 证据出处 | 优先级 |
|---|---|---|---|
| **R1** | 分片级**重复内容检测**：多个分片字节完全相同 ⇒ 判定为污染 | §4.2（6 个连续分片逐字节相同） | **P0** |
| **R2** | 命中污染时**明确失败并说明原因**，绝不产出坏 mp4 | §5（退出码 0 的假成功） | **P0** |
| **R3** | 实测分片时长 vs `#EXTINF` 声明值偏差校验（诱饵恒 8 s ≠ 声明 5 s） | §2、§5 | P1 |
| **R4** | **AES-128 原生解密**（C# 取分片 → 解密 → 拼接 → ffmpeg `-c copy` 重封装） | §3（真实流就是 AES-128） | P1 |
| **R5** | 对"无法绕过的污染"如实报告缺失段落，而不是无限重试 | §4.3 | P1 |

> R1 + R2 是**与架构选择无关**的必备项：无论最终走 ffmpeg 直连还是 C# 原生取片，都必须先能识别"这条地址是坏的"。

## 7. 需要拍板的两个问题

| # | 问题 | 建议 |
|---|---|---|
| 1 | 污染无法移除时，是否接受**部分成功**（把好分片拼成 mp4，并在结果里标出缺失的时间段）？还是宁可整体失败？ | 建议"部分成功 + 明确标注"，比整条失败有用 |
| 2 | 是否现在就把下载链路切到 **C# 取分片 + AES-128 解密 + ffmpeg 仅做封装**？（这是落实 R1/R3/R4 的唯一途径） | 建议切；ffmpeg 直连无法做分片级校验与重试 |

## 8. 还需要你确认的一点

上面两条地址是**从播放页面的 Network 面板复制的**，还是**由本工具嗅探出来的**？

- 如果是页面实际播放用的地址 —— 说明站点自身的播放也是坏的（页面拿到了诱饵）；
- 如果是工具嗅探出来的 —— 需要排查嗅探链路是否把 `#EXT-X-TOKEN` 这类关键参数弄丢了。

这个信息决定了下一步是先查嗅探器还是先改下载器。
